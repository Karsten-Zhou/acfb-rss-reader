# Browser Push Notifications

How the RSS Reader sends native browser/OS notifications for newly discovered
articles. Uses the standard **Web Push API** with a service worker, VAPID keys
and the `web-push` library — no third-party push SaaS.

## Why Web Push instead of a push SaaS

This is a personal, single-user application. Cloudflare's free tier is more
than enough, and the standard Web Push API is:

- **Free** — no per-notification or per-device pricing.
- **Native** — notifications look and behave like OS notifications, work
  offline, and integrate with browser permission controls.
- **Private** — articles are delivered straight from our Worker to the
  browser; no third party sees who subscribes or what gets sent.
- **Standardized** — built into every major browser (Chrome, Edge, Firefox,
  Safari 16+, Samsung Internet).

Third-party push SaaS (Firebase Cloud Messaging, OneSignal, …) adds cost,
a dependency, another privacy boundary and complexity that a single user
doesn't need.

## Architecture

```
Browser
  │ Service worker (public/sw.js) receives push + shows native notification
  │ Push API creates a PushSubscription on subscribe
  ▼
Worker API (Hono)
  │   PUT /api/push/subscription        (create/update, authenticated)
  │   DELETE /api/push/subscription/:id (remove, authenticated)
  │   GET  /api/push/key | /api/push/capability
  ▼
D1  push_subscriptions (per device) + notification_deliveries (idempotency)
  ▲
Refresh pipeline (refreshFeed) detects genuinely-new entries
  │
  ▼
notification service → web-push → Web Push endpoint → browser
```

The existing feed-refresh pipeline (cron → `RefreshWorkflow` → `refreshFeed`)
is the **single** source of truth for what counts as a new article. There is
no second mechanism that independently decides whether an article is new.

## Data model (D1)

Generated by `server/db/schema/notifications.ts` (migration `0002_*.sql`).

### `push_subscriptions`

One row per browser/device subscription. A single user can have several
(desktop Chrome, Android Chrome, Firefox, multiple profiles).

| Column                                  | Purpose                                                        |
| --------------------------------------- | -------------------------------------------------------------- |
| `id`                                    | Internal subscription id (PK)                                  |
| `user_id`                               | Owning user (FK → `users`)                                     |
| `endpoint`                              | Push-service capability URL. **Sensitive** — unique per sub    |
| `expiration_time`                       | When the subscription expires, or NULL                         |
| `p256dh`, `auth`                        | Encryption keys (URL-safe base64) used by `web-push`           |
| `created_at` / `updated_at`             | Audit timestamps                                               |
| `last_delivered_at` / `last_failure_at` | Delivery telemetry                                             |
| `failure_count`                         | Consecutive failures; drives auto-deactivation                 |
| `active`                                | Deactivated when the push service reports the endpoint invalid |

The `endpoint` is the unique key: re-subscribing the same device updates the
row instead of creating a duplicate.

### `notification_deliveries`

The **idempotency ledger**. One row per `(entry_id, notification_type)`.

| Column                        | Purpose                                                |
| ----------------------------- | ------------------------------------------------------ |
| `entry_id`                    | FK → `entries` (composite PK with `notification_type`) |
| `notification_type`           | Currently only `new-feed-entry`                        |
| `status`                      | `sending` → `sent` / `failed`                          |
| `created_at` / `delivered_at` | Timestamps                                             |
| `target_count`                | Number of active subscriptions attempted               |

It does **not** duplicate the article — it's a lightweight key that says "we
already notified for this article", which is what makes retries safe.

## VAPID keys

Web Push auth uses a VAPID key pair. The keys must be **stable**: generating a
new pair on every deploy would invalidate all existing subscriptions.

### Generate

```sh
bunx web-push generate-vapid-keys --json
# {"publicKey":"...","privateKey":"..."}
```

### Configure locally (`.dev.vars`, gitignored)

```
VAPID_PUBLIC_KEY=<publicKey>
VAPID_PRIVATE_KEY=<privateKey>
VAPID_SUBJECT=mailto:you@example.com
```

### Configure in production (Worker secrets)

```sh
bunx wrangler secret put VAPID_PUBLIC_KEY
bunx wrangler secret put VAPID_PRIVATE_KEY
bunx wrangler secret put VAPID_SUBJECT
```

The **private key never leaves the server** — it is only ever read in
`server/notifications/vapid.ts` and used by `web-push` to sign requests. The
public key is served to the browser (the Push API requires it as the
`applicationServerKey`). `VAPID_SUBJECT` is a `mailto:` or `https://` URI that
identifies the app to the push service.

## Local development

1. Generate a VAPID key pair (once):

   ```sh
   bunx web-push generate-vapid-keys --json
   ```

2. Copy `.dev.vars.example` to `.dev.vars` (or add to an existing one) and
   paste the values:

   ```
   VAPID_PUBLIC_KEY=<publicKey>
   VAPID_PRIVATE_KEY=<privateKey>
   VAPID_SUBJECT=mailto:you@example.com
   ```

   Use the **same** keys for local and production so a subscription created
   in local dev stays valid if you deploy, and vice-versa.

3. Apply migrations: `bunx wrangler d1 migrations apply rss-reader-db --local`
   (or `--remote` if your dev uses remote bindings).

4. `bun run dev` → `http://localhost:8787`.

5. Sign in, open **Settings**, enable **Browser notifications**.

> **Important for local testing:** the Push API requires a **secure context**.
> `http://localhost` is treated as a secure context by Chrome/Edge/Firefox (so
> service-worker registration and notifications work), but Safari does _not_
> treat plain `http://localhost` as secure for push. To test in Safari, or to
> test on a phone, run the dev server through a tunnel that provides HTTPS
> (e.g. `cloudflared tunnel --url http://localhost:8787`) and set
> `APP_ORIGIN` to that HTTPS origin.
>
> On desktop Chrome/Edge/Firefox (`http://localhost`), you can verify
> end-to-end without deploying: sign in, enable notifications, then trigger a
> feed refresh (e.g. add a feed and click **Refresh**) and a notification
> should appear even when the tab is in the background.

## Enable in the app

Settings → **Browser notifications**:

- The switch is **per device**: it subscribes/unsubscribes only the current
  device. Other devices are unaffected — you can e.g. turn notifications off
  on your desktop while keeping them on your phone. There is no global
  on/off preference; a device receives notifications if and only if it holds
  an active subscription.
- Turning it on runs the subscribe flow: register the service worker →
  request notification permission (only from this explicit click) → fetch the
  VAPID public key → create the browser `PushSubscription` → persist it
  server-side.
- Turning it off unsubscribes the browser and removes the server-side
  subscription row.

## Notification lifecycle

1. Cron triggers `RefreshWorkflow`; it chunks due feeds and runs
   `refreshFeed` for each.
2. `refreshFeed` downloads, parses and **deduplicates** via
   `ingestFeed` (by `feed_id` + `guid`).
3. Only genuinely-new entries (newly inserted) are passed to
   `notifyNewEntry`.
4. `notifyNewEntry`:
   - Checks VAPID is configured.
   - Loads the user's **active** subscriptions; none ⇒ skip (notifications
     are opt-in per device — there is no global on/off preference).
   - **Claims the idempotency row** with `INSERT … ON CONFLICT DO NOTHING`
     into `notification_deliveries`. If the (entry, type) row already exists,
     nothing is sent — this is what prevents duplicates across refreshes,
     Workflow retries and Worker restarts.
   - Sends to every **active** subscription via `web-push` (with a compact,
     encrypted payload).
5. Dead endpoints (push service 404/410) are deactivated and skipped; the
   remaining subscriptions still get the notification. Endpoints that fail
   generically accumulate a failure count and are auto-deactivated after 3
   consecutive failures.
6. First import of a brand-new feed or an OPML import does **not** notify the
   historical backlog — only entries discovered during a subsequent refresh
   of an existing feed are considered new.

## Payload

The (encrypted) push payload is deliberately small and never contains article
body/html:

```jsonc
{
  "type": "new-feed-entry",
  "title": "Feed Title",
  "body": "Article title",
  "tag": "feed-entry:42",
  "url": "/reader/42",
  "entryId": 42,
  "feedId": 7,
}
```

## Click behavior

Clicking a notification (`notificationclick` in `public/sw.js`):

1. Closes the notification.
2. Focuses an existing app window if there is one (and navigates it to
   `/reader/<entryId>`), avoiding a duplicate window.
3. Otherwise opens a new window/tab at `/reader/<entryId>`.

`/reader/:entryId` is an authenticated SPA route; `AppView` watches the param
and selects/opens the article. If the user is signed out, the router redirects
through the login flow and preserves the destination.

## Disabling notifications

- **Per device**: Settings → Browser notifications → switch off
  (unsubscribes the browser and removes the server-side row). Other devices
  keep receiving notifications.
- **Blocked permission**: If the browser blocks notifications, the UI shows a
  "denied" state and points to the browser's site-permission settings; the app
  won't keep re-prompting.

## Invalid-subscription cleanup

- Endpoints that return 404/410 from the push service are deactivated
  immediately and skipped on future sends.
- Endpoints that fail with other errors are deactivated after 3 consecutive
  failures.
- Deactivated rows can be purged via `POST /api/push/cleanup`
  (`cleanupInactiveSubscriptions`), or are deleted when a device unsubscribes.

## Browser support

| Browser          |   Push   | Payload  | Notes                                                          |
| ---------------- | :------: | :------: | -------------------------------------------------------------- |
| Chrome / Edge    |    ✅    |    ✅    | Requires HTTPS (or `localhost`)                                |
| Firefox          |    ✅    |    ✅    | Delivery quota exempt for shown notifications                  |
| Safari           | ✅ (16+) | ✅ (16+) | macOS 13+; needs a Web Push certificate linked in the manifest |
| Android Chrome   |    ✅    |    ✅    | Requires installing as a PWA                                   |
| Samsung Internet |    ✅    |    ✅    | Payload support varies by version                              |

The app degrades gracefully: if Push/Notifications aren't supported, the
Settings UI shows an "unsupported" state and the rest of the app works
unchanged. iOS Safari gained Web Push in 16.4 but only for installed PWAs.
